[Alchemy](https://alchemy.run/) v2 declares infrastructure and Worker code in one TypeScript program and reads configuration through `effect/Config`. Its [`secrets` option](https://alchemy.run/environments/secret-providers/) lets a stack choose where those values come from. This package is that provider for varlock:

- Your `.env.schema` is resolved and validated (plugins, `.env` files, `@currentEnv`) before alchemy builds any provider. Values become the stack's `Config` source, so alchemy's own reads (Cloudflare credentials included) come from varlock.
- Every schema item is available as a typed Worker binding. `@sensitive` items upload as secrets, everything else as plain text or JSON.
- The `__VARLOCK_ENV` blob rides along, so `@varlock/cloudflare-integration/init` gives the Worker [log redaction and leak detection](/integrations/cloudflare/#log-redaction-and-leak-prevention) and a typed `ENV`.
- Deploy credentials stay out of Workers: in a multi-service stack the root schema is never bound, and for a single schema `bindingsFilter` (for example `"!#deploy"`) keeps tagged items out of the bindings and the blob while alchemy can still read them.

:::note[Alchemy version]
Requires alchemy 2.0.0-beta.80 or later (the release with the `secrets` stack option). The snippets below import Cloudflare from `@alchemy.run/cloudflare`, the separate package beta.84 moved it to (its version must match `alchemy`); on beta.80 to beta.83 the same resources are `alchemy/Cloudflare` inside the core package. On older versions, `import "varlock/auto-load"` at the top of `alchemy.run.ts` still works; see [Deploying with Alchemy](/integrations/cloudflare/#deploying-with-alchemy).
:::

## Setup

<Steps>
1. **Install the packages** in the package that holds `alchemy.run.ts`

    <InstallJsDepsWidget packages="@varlock/alchemy-integration @varlock/cloudflare-integration varlock" />

    On alchemy 2.0.0-beta.84 or later, Cloudflare resources live in a separate package, so install it next to `alchemy`:

    <InstallJsDepsWidget packages="@alchemy.run/cloudflare" />

1. **Create a `.env.schema`** next to `alchemy.run.ts` (run `varlock init` to migrate an existing `.env`). Tag deploy credentials so they can be filtered out of the Worker; keep tokens only varlock uses `@internal`.

    ```env-spec title="packages/infra/.env.schema"
    # @generateTypes(lang=ts, path=env.d.ts)
    # @currentEnv=$APP_ENV
    # ---
    # @type=enum(development, preview, production)
    APP_ENV=development

    # bound into the Worker
    # @sensitive
    BETTER_AUTH_SECRET=
    # @type=url
    CORS_ORIGIN=http://localhost:4321

    # read by alchemy at deploy time; kept out of the Worker by bindingsFilter below
    # @tag(deploy)
    CLOUDFLARE_ACCOUNT_ID=
    # @tag(deploy) @sensitive
    CLOUDFLARE_API_TOKEN=
    ```

1. **Wire the stack**

    ```ts title="alchemy.run.ts"
    import * as Alchemy from "alchemy";
    import * as Cloudflare from "@alchemy.run/cloudflare";
    import * as Effect from "effect/Effect";
    import * as Varlock from "@varlock/alchemy-integration";
    import type { CoercedEnvSchema } from "./env.d.ts"; // generated by @generateTypes

    const env = Varlock.Secrets<CoercedEnvSchema>({
      // deploy credentials feed alchemy's Config but never become Worker bindings
      bindingsFilter: "!#deploy",
    });

    export default Alchemy.Stack(
      "app",
      { providers: Cloudflare.providers(), state: Cloudflare.state(), secrets: env },
      Effect.gen(function* () {
        const bindings = yield* env.bindings;
        const api = yield* Cloudflare.Worker("api", {
          main: "./src/worker.ts",
          compatibility: { flags: ["nodejs_compat"] },
          env: { ...bindings, BETTER_AUTH_URL: Cloudflare.Worker.URL },
        });
        return { api: api.url };
      }),
    );
    ```

1. **Boot varlock inside the Worker**

    ```ts title="src/worker.ts"
    import '@varlock/cloudflare-integration/init';
    import { ENV } from 'varlock/env';
    ```

    `nodejs_compat` must be enabled, as with every Cloudflare deploy of varlock.
</Steps>

`alchemy dev`, `alchemy deploy`, and the other commands need no wrapper: alchemy calls varlock while building the stack session. The provider is an ordinary `secrets` entry, so it composes with alchemy's others: a stack that declares `secrets` no longer reads `.env` or accepts `--env-file` on its own, and the process environment stays the implicit last entry (list `Alchemy.Secrets.ProcessEnv()` first to rank it below varlock). varlock already treats ambient env vars as overrides, so the default order gives the same answer either way.

## Environments and stages

While varlock resolves, the alchemy run is visible to the schema as `ALCHEMY_STACK`, `ALCHEMY_STAGE`, and `ALCHEMY_DEV` (`true` under `alchemy dev`). The package ships a schema fragment that declares them and derives an environment name, `ALCHEMY_ENV`, from them. Copy it into your schema and point `@currentEnv` at it:

```env-spec
# @currentEnv=$ALCHEMY_ENV
# ---
# @optional @public
ALCHEMY_STAGE=
# @type=boolean @optional @public
ALCHEMY_DEV=
# @type=enum(development, preview, staging, production, test) @public
ALCHEMY_ENV=if($ALCHEMY_DEV, development, remap($ALCHEMY_STAGE, regex("^(prod|production)$"), production, regex("^(staging|stage)$"), staging, "test", test, undefined, development, regex(".*"), preview))

# @type=url
CORS_ORIGIN=http://localhost:4321   # .env.preview and .env.production override this
```

| alchemy run | `ALCHEMY_ENV` | loads |
| --- | --- | --- |
| `alchemy dev` (any stage) | `development` | `.env.development` |
| `--stage production` or `prod` | `production` | `.env.production` |
| `--stage staging`, `--stage test` | `staging`, `test` | `.env.staging`, `.env.test` |
| any other stage (`dev_sam`, `pr-42`, ...) | `preview` | `.env.preview` |
| no stage (plain `varlock load`) | `development` | `.env.development` |

The mapping is ordinary schema logic, so change it like any other value: match your own stage names with [`remap()`](/reference/functions/#remap) (for example `regex("^pr-")` to a `pr` environment and `regex("^dev_")` to `sandbox`), or drop `ALCHEMY_ENV` and derive your own flag. The `env` option in `alchemy.run.ts` can also set any of these from `{ stack, stage, dev }`, and an ambient value overrides the schema's. varlock's own `VARLOCK_ENV` is left alone. (The fragment is `.env.schema` inside the package; once [package imports](/guides/import/) land you will be able to `@import(npm:@varlock/alchemy-integration/.env.schema)` instead of copying it.)

Alchemy treats moving a stage between local emulation (`alchemy dev`) and live (`alchemy deploy`) as a replacement of every resource, so deploy to a named stage (`--stage preview`) rather than the personal `dev_<user>` stage you develop on.

## Several services, one stack

In a monorepo each service usually owns its schema. Pass `services` to load one schema per service (plus a root schema next to `alchemy.run.ts` for deploy credentials and shared config) and hands out per-service bindings, each with its own `__VARLOCK_ENV` blob:

```ts title="packages/infra/alchemy.run.ts"
import * as Varlock from "@varlock/alchemy-integration";
import type { CoercedEnvSchema as ServerEnv } from "../../apps/server/env.d.ts";
import type { CoercedEnvSchema as WebEnv } from "../../apps/web/env.d.ts";

const env = Varlock.Secrets<{ server: ServerEnv; web: WebEnv }>({
  services: { server: "../../apps/server", web: "../../apps/web" },
});

// inside the Stack effect:
const server = yield* Cloudflare.Worker("server", {
  main: "../../apps/server/src/index.ts",
  env: { DB: db, ...(yield* env.bindingsFor("server")), BETTER_AUTH_URL: Cloudflare.Worker.URL },
});
```

All schemas feed the stack's `Config` (the root schema wins on duplicate keys), but only service schemas produce bindings: the root schema is deploy-process config by definition, so Cloudflare credentials there never need a tag. Pass `root: false` if the infra package has no schema of its own, or `{ path, filter, bindingsFilter }` per service to select a subset with a [filter expression](/reference/cli-commands/#filtering-items).

## Validation and injection only, no varlock runtime

If the Worker does not use `varlock/env` or `@varlock/cloudflare-integration/init`, pass `blob: false`. varlock still validates the schema, resolves plugin-backed values, feeds alchemy's `Config`, and produces the typed bindings; the Worker just receives plain Cloudflare vars and secrets, read through `env` as usual:

```ts title="alchemy.run.ts"
const env = Varlock.Secrets<CoercedEnvSchema>({ blob: false });

// in the Stack effect:
const api = yield* Cloudflare.Worker("api", {
  main: "./src/worker.ts",
  env: { ...(yield* env.bindings) },
});
```

```ts title="src/worker.ts"
import { env } from "cloudflare:workers";

export default {
  async fetch() {
    return new Response(env.CORS_ORIGIN); // plain string; secrets arrive as plain strings too
  },
};
```

`@sensitive` items still upload as `secret_text` and everything else as plain text or JSON. What you give up is the in-Worker layer only: log redaction, response leak scanning, and the typed `ENV` proxy. With `Secrets({ services })`, set it per service (`server: { path, blob: false }`).

## Types

`Cloudflare.InferEnv` derives a Worker's `Env` type from its `env` prop, so the bindings you spread need static keys. Pass the `CoercedEnvSchema` type from the schema's generated `env.d.ts` as the type argument (`Varlock.Secrets<CoercedEnvSchema>()`), and the Worker's `Env` gets every schema key with the right type. Strings, numbers and booleans keep their coerced type (numbers and booleans upload as JSON bindings). Arrays and objects arrive as their process.env string form (`one,two`, or JSON for objects), because a sensitive composite can only travel as a `secret_text` string; the blob keeps the parsed value, so `ENV.LIST` through the varlock runtime is still an array. Keep the resource definition in a function if other packages import the inferred type:

```ts
const makeServer = (bindings: VarlockBindings<ServerEnv>) =>
  Cloudflare.Worker("server", { main: "...", env: { DB: db, ...bindings } });
export type ServerWorkerEnv = Cloudflare.InferEnv<ReturnType<typeof makeServer>>;
```

## Options

- `path`: directory holding the schema; defaults to the directory alchemy runs in.
- `filter`: varlock `--filter` expression; items outside it are neither resolved nor bound, and do not reach alchemy's `Config` either.
- `bindingsFilter`: same syntax, applied after resolution to decide which items become bindings and enter the blob. Everything still reaches alchemy's `Config`. `@required` is not available here.
- `blob`: `false` leaves `__VARLOCK_ENV` out of the bindings (no in-Worker runtime); `{ maxBytes }` changes the chunk size from Cloudflare's 5KB secret limit for another platform.
- `env`: `({ stack, stage, dev }) => Record<string, string>` of extra env vars to expose to varlock while it resolves, on top of `ALCHEMY_STACK`, `ALCHEMY_STAGE`, and `ALCHEMY_DEV`. An ambient value overrides what the schema derives.

## Things to know

- `effect` must resolve to a single copy in your project. The package peer-depends on it, like alchemy does; two copies make alchemy unable to read the `Redacted` values this package produces (`Unable to get redacted value`).
- During `alchemy login` (auth-provider discovery) the provider contributes nothing, so a schema whose values come from a vault does not block configuring the very credentials it needs.
- Resolution happens once per alchemy session (each `deploy`, `plan`, or dev reload). Plugin-backed items are resolved then, so a 1Password or AWS lookup runs per session, not per Worker.
- Cloudflare secrets are capped at 5KB. A larger blob is split into `__VARLOCK_ENV_CHUNKS` and `__VARLOCK_ENV_<n>` bindings automatically; the runtime reassembles them.
- With `Alchemy.localState()`, alchemy persists every `Redacted` value, including the blob, in plaintext under `.alchemy/state/`. Use `Cloudflare.state()`, which encrypts state at rest. An encrypted local state store backed by varlock's local encryption is planned for a later release.
- Values that only exist after deploy (a sibling Worker's URL) are alchemy Outputs, not varlock items. Add them to `env` next to the spread, as `BETTER_AUTH_URL` above.
