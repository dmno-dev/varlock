The built-in `keychain()` resolver lets you load secrets directly from the **macOS Keychain** using declarative instructions in your `.env` files. It communicates with the Keychain through Varlock's native Swift daemon, which enforces biometric authentication (Touch ID) and per-session access control.

:::note[Built-in support]
No plugin installation is required. `keychain()` is built into Varlock and available on macOS.
:::

:::tip[Or use `varlock()`]
If you don't already have secrets stored in your macOS Keychain, you may want to use the [`varlock()` resolver](/guides/local-encryption) instead. It provides the same biometric-gated, device-local encryption benefits without needing to manage Keychain items, and it works cross-platform.

See the [local encryption guide](/guides/local-encryption/) for more details.
:::

## Features

- **Built-in**: no plugin or extra dependency needed
- **Biometric gating**: secret reads are protected by Touch ID via Varlock's native daemon
- **Interactive picker**: use `keychain(prompt)` to browse and select items via a native dialog
- **Auto-write-back**: prompt mode writes the resolved reference back to your config file
- **Named or positional syntax** for quick or precise lookups
- **Metadata fields**: read an item's account, label, service, or server instead of its secret
- **Multiple keychain support**: access the login, System, or custom keychains

:::caution
`keychain()` is only supported on **macOS**. If your team includes non-Mac developers, see [other platforms and optional items](#other-platforms-and-optional-items).
:::


## Getting started
Rather than wiring up items individually, the easiest way to get started is by using `keychain(prompt)`. This will open a native picker dialog where you can select existing keychain items, or create new ones. After selection, Varlock will automatically write the resolved reference back into your config file for future use.

```env-spec add="keychain(prompt)"
ITEM=keychain(prompt) # Opens a native picker dialog
```

## Import plaintext env files

If you already have sensitive plaintext values in a local `.env` file, import them into macOS Keychain and replace the plaintext with stable `keychain(...)` references. The file to import is the first argument:

```sh
varlock keychain import .env --profile jb
```

By default this **edits the file in place**: each sensitive plaintext value is replaced by its `keychain(...)` ref, so the secret no longer lives on disk. Comments and non-sensitive values are left untouched. To write the refs to a *different* file instead and leave the source as-is, pass `--write-to`:

```sh
varlock keychain import .env --profile jb --write-to .env.jb
```

Import requires an existing `.env.schema` file for the input env file so Varlock knows which input variables are secrets and which are not. It only imports variables marked `@sensitive` in that schema and never prints secret values. Re-running is safe: values already converted to `keychain(...)` refs are skipped. By default, Varlock refuses to overwrite an existing Keychain item (or, with `--write-to`, an existing ref in the target file); pass `--force` to overwrite.

The file you name must be one Varlock loads as part of your env setup. It resolves your normal env graph (from `package.json` `varlock.loadPath`, or the files in the current directory) to read sensitivity from your schema, the same way `varlock encrypt --file` works. An arbitrary file outside that setup can't be imported. The value stored in Keychain is taken from the file you named specifically; an override of the same variable in another file (such as `.env.local`) does not change what gets imported.

Generated refs use `service="varlock"` and account names like `<project>:<profile>:<ENV_VAR>`. The profile defaults to `local`, and the project defaults to the current directory name. Both can be overridden:

```sh
varlock keychain import .env --profile jb --project my-app
```

## Set one secret manually

To store one secret without putting the value in shell history, run `set` and enter the value at the masked prompt:

```sh
varlock keychain set API_KEY --profile jb --write-to .env.jb
```

This stores the item under `service="varlock"` with account `<project>:<profile>:API_KEY`, then writes the matching `keychain(...)` ref when `--write-to` is provided. If you need to paste a multi-line secret, pipe it through stdin instead of passing it as a command-line argument:

```sh
cat secret.txt | varlock keychain set PRIVATE_KEY --profile jb --write-to .env.jb
```

By default, `set` refuses to overwrite an existing Keychain item or env ref. Pass `--force` to replace both.

## Share refs with your team

Keychain items live on each developer's own machine, but the `keychain(...)` refs that point at them can be committed. When a teammate loads a ref whose item they don't have yet, Varlock fails with the exact command to create it, for example:

```sh
varlock keychain set API_KEY --service varlock --account my-app:jb:API_KEY
```

Running that command stores their own value under the same service and account, so the committed ref resolves for them too. Varlock never creates missing items on its own during `load` or `run`.

## Other platforms and optional items

Reading a `keychain()` value on Linux or Windows is an error, but a `keychain()` call in a branch that does not run is fine. To give non-Mac teammates another source, either branch on the OS with [`if()`](/reference/functions/#if), which only resolves the branch it picks:

```env-spec
API_KEY=if(eq($VARLOCK_OS, "darwin"), keychain("my-app", account="api"), op("op://dev/api/credential"))
```

or keep the shared source in `.env.schema` and let Mac users point at their Keychain in their own git-ignored `.env.local`:

```env-spec title=".env.local"
API_KEY=keychain("my-app", account="api")
```

For an item that may legitimately not exist, add `allowMissing=true`. A missing item then resolves to empty instead of failing, so [`fallback()`](/reference/functions/#fallback) moves on to the next value:

```env-spec
API_KEY=fallback(keychain("my-app", account="api", allowMissing=true), "default-value")
```

`allowMissing` only covers a missing item. Running on another OS, access denied, a cancelled prompt, or a daemon error still stop the load. Without it, a teammate who has not stored the item gets an error with the `varlock keychain set` command to fix it, which is usually what you want for required secrets.

## Delete an item

To remove an item, pass its account (and `--service` if it does not use the default `varlock` service):

```sh
varlock keychain delete --account "my-app:jb:API_KEY"
```

`delete` removes exactly one item, matched by service and account, and fails if no matching item exists.

## Access management

When a `keychain()` ref points at an item that Varlock did not create (for example one added by another app or managed by your IT department), macOS may prompt the first time VarlockEnclave reads it. Choose **Always Allow** to add VarlockEnclave to that item's access list so later reads do not prompt. **Allow** only covers the current read, so you will be asked again next time.

If you clicked **Deny**, or want to grant access ahead of time, use `fix-access`. It adds VarlockEnclave to the item's access list; macOS may ask for your login password to approve the change.

```sh
varlock keychain fix-access --account "my-app:jb:API_KEY"
```

`--service` defaults to `varlock`, but can be overridden for legacy or manually-created Keychain items:

```sh
varlock keychain fix-access --service "com.company.api" --account "admin"
```

You can also fix every explicit `keychain(...)` ref in an env file:

```sh
varlock keychain fix-access --path .env.jb
```

## List Keychain items

To see which Keychain items are available, list them. This shows metadata only (service, account, and keychain) and never reads secret values:

```sh
varlock keychain list           # same as bare `varlock keychain`
varlock keychain list API_KEY   # filter (matches service, account, or label)
```

Pass `--keychain` to search a specific keychain, such as `System`:

```sh
varlock keychain list --keychain System
```

#### `keychain()`

Fetch a secret from the macOS Keychain. Communicates with the Keychain through Varlock's native daemon, which enforces biometric (Touch ID) authentication.

**Array args:**
- `service` (optional): Service name of the keychain item (positional shorthand). Can be combined with the key/value args below.
- `prompt` (optional): Enter interactive picker mode

**Key/value args:**
- `service` (optional): Service name of the keychain item. Use either this or the positional form, not both.
- `account` (optional): Account identifier for the keychain item. Can be used without a service.
- `keychain` (optional): Name of a specific keychain to search (e.g., `"System"`)
- `field` (optional): Return one of the item's metadata attributes instead of its secret: `account`, `label`, `service`, or `server`
- `allowMissing` (optional): If `true`, resolve to empty instead of failing when the item does not exist. Useful inside `fallback()`. Does not cover running on another OS.
- `prompt` (optional): If set, opens a native picker dialog for interactive selection

```env-spec /keychain\\(.*\\)/
# Positional shorthand
DATABASE_PASSWORD=keychain("com.company.database")

# Named service param
API_KEY=keychain(service="com.company.api")

# With account
ADMIN_PW=keychain("com.company.db", account="admin")

# Targeting a specific keychain
CERT=keychain("com.company.cert", keychain="System")

# Metadata field (returns the account name, not the secret)
DB_USER=keychain("com.company.db", field="account")

# Optional item with a fallback source
OPTIONAL=fallback(keychain("com.company.opt", allowMissing=true), "default-value")

# Interactive picker mode
NEW_SECRET=keychain(prompt)
```

## Troubleshooting

### "keychain() is only supported on macOS"
This resolver requires macOS. It is not available on Linux or Windows. See [other platforms and optional items](#other-platforms-and-optional-items) for ways to use another source there, or consider one of the [plugin-based secret sources](/plugins/overview).

### "Keychain item not found"
No item matches the ref. For a ref with both a service and an account, the error prints the `varlock keychain set ...` command that creates it. Otherwise, check the service and account with `varlock keychain list`, or use `keychain(prompt)` to pick the item.

### "Varlock is not allowed to read this Keychain item"
The item exists but VarlockEnclave is not on its access list, or access was denied in the macOS prompt. Run the `varlock keychain fix-access ...` command the error prints. See [access management](#access-management).

### "More than one Keychain item matches"
Several items share the service. Add `account="..."` to the ref to pick one; `varlock keychain list` shows the candidates.

### Selection was cancelled
If you dismiss the native picker without selecting an item, the resolution will fail. Run `varlock` again to retry, or replace `keychain(prompt)` with an explicit `keychain(service="...")` reference.
